# Coding jobs and disposable execution

Chief dispatches coding work through owner-scoped tools. A durable controller in the existing service provisions one CodeBuild environment at a time. A separate [Python 3.12+ runtime](../coding_runtime/README.md) in an immutable image inspects the pinned repository, plans, changes files, verifies and obtains a separate reviewer-context verdict. Chief's conversational turn can end while the worker continues. The live gateway never executes coding shell commands.

## Request and result

Tell Chief about the bug or feature in ordinary conversation. No slash command is required. Chief clarifies missing requirements and dispatches a planning job, then shows the complete requirement brief for confirmation. Every new `coding_start` job begins in `plan`, including a legacy `mode: implement` request. Planning is read-only and stops at a brief or question; it does not authorise implementation.

Only the allowed owner can confirm the exact delivered brief using its **Approve requirements** button or a direct text reply such as **yes** to that message. Unbound conversational affirmations and model arguments are not confirmation authority. The host binds delivery receipt, owner/private chat, current revision, original objective/context, pinned base/settings, plan and carried artifact. Confirmation expires after 15 minutes; uncertain delivery, stale messages, changed scope and another owner cannot grant implementation. The approved scope is queued once, in a new Python sandbox, after planning cleanup completes. Implementation cannot replace the approved plan. Scope changes go through a new planning/confirmation cycle; explicit resume of unchanged approved work preserves the brief.

`coding_status(id?)` reads jobs and saved plans. `coding_reply(id, baseRevision, requestKey, message, mode?)` supplies clarifications/scope changes and replans; mode implement cannot bypass confirmation. `coding_resume` on a completed plan requests its confirmation card without spawning another planner; on a paused job it explicitly resumes the same authorised scope after cleanup. `/continue` and ordinary `work_*` tools do not control coding jobs. Originating Telegram thread, repository, main branch, image, models and allocations remain host authority. No model or worker can call the owner-confirmation path, merge or deploy its own candidate.

Start and revision request keys are idempotent only for identical requests. Preserve exact IDs and revisions. The original objective, supplied context and follow-up revisions are private. A worker receives only its assignment, configured source repository and saved checkpoint, not Chief's conversation, memory or personal integrations.

The complete protected owner objective/context must fit a bounded UTF-8 request envelope, with room reserved for tools and observations. Start and resume reject oversized owner instructions before provisioning and ask for a concise brief; they never silently truncate them. Saved plans and progress summaries are separately paginated in both coding and review, so a large generated plan cannot prevent resumption. Review approval is rejected until contiguous page delivery covers the complete plan. Large source artifacts remain inspectable through the checkout.

## Lifecycle and recovery

The separate tables in migration 024 retain jobs, revisions, ordered progress events and private model-call journals. The host claims a lease before external work; an index allows one active or cleanup-pending sandbox globally. States are `queued`, `provisioning`, `running`, `plan_ready`, `awaiting_input`, `publishing`, `pr_ready`, `paused`, `failed`, `cancelled`. Cleanup is independently `none`, `pending` or `complete`. The coding allocation begins at the first worker heartbeat, with a separate bounded provisioning allowance; the reviewed defaults are 15 active minutes, 40 model calls and 100 model tool calls. Changing this allocation does not change Chief's allocations or provider price ceilings. Model usage and provider metadata are private job events; sandbox billing and measured coding quality remain separate.

Chief restart recovery does not pause or replay coding jobs. The next controller tick reconnects by sandbox ID. Missing heartbeats, expired allocation or a worker that exits without a recorded result pause the job. Saved files, plan and patch remain available. A new attempt needs an explicit owner resume and completed sandbox cleanup. Unknown create responses are reconciled through the attempt ID; they never cause another `StartBuild`. CodeBuild is configured without automatic retries. If no identity can be found in the bounded provider history, keep cleanup pending and have an authorized operator inspect the provider before settling the job. Do not directly set cleanup complete without evidence that no worker can still run.

Worker tokens are HMAC-derived from job and attempt IDs and a host key. They authorise only bounded worker endpoints, expire with the attempt and stop authorising work after cancellation or completion. The worker has no database, GitHub App, production model or Telegram credential. Model calls go through a job-scoped proxy using the existing OpenRouter adapter and price routing. Call IDs journal successful responses for reconciliation; pending or uncertain model calls are never replayed under the same ID. Diagnostic copies are filtered, while exact responses are encrypted with a derived key so a retry preserves source text rather than replaying a scrubbed approximation. Key rotation requires idle workers and reviewed rewrapping of retained response boxes. Model histories/results remain in private storage, not Actions logs.

The trusted CodeBuild launcher is a root shell that drops to UID/GID 1000 with no new privileges and all capabilities removed. It never executes repository code itself. Python runs with `-I` and sets PR_SET_DUMPABLE=0 through ctypes before loading credentials or repository code. This blocks same-UID commands from reading its private environment, memory or descriptors through /proc. Commands receive a stripped environment. Linux subreaper adoption and serialized command cleanup terminate/reap detached descendants; a separately closable output transport bounds pipe cleanup. The immutable package is root-owned outside the checkout. CI exercises the actual Linux process boundary. The legacy Node launcher is retained only for already-pinned Node jobs/images, with its original `--disable-sigusr1` and N-API guard. `settings.runtime` selects a fixed host launcher, never a model-provided command. Change the Python selector and Python digest together. The sandbox remains the execution boundary; host CI and independent published-head review remain mandatory before merging.

Chief's production OpenRouter adapter remains the credential and journal boundary. The Python `ChiefOpenRouter` adapter speaks that versioned gateway protocol; it never receives a provider key. New coding jobs use `deepseek/deepseek-v4.1-flash` with high effort; review stays on `openai/gpt-6.1-sol`. Existing price ceilings and allocations are unchanged. OpenRouter reasoning details survive tool continuations unmodified; oversized histories discard complete old call groups. This preserves the [OpenRouter reasoning contract](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).

Worker tools are file read/write/delete, bounded commands, a paginated read of the saved plan and reports. Planning and review tools enforce read-only command forms. Verification runs the three required repository scripts from the resulting checkout. Tool homes and npm/XDG caches live outside the checkout so required dependency installation cannot enter the Git artifact. Review uses a fresh checkout with the same changes and empty model history; it reads a labelled plan preview plus complete paginated plan and cannot implement its findings. Failed checks or requested changes return to the coding context within the same allocation. Checkpoints support regular UTF-8 files only, at most 100 changed files and bounded patch/content sizes; binary and symlink changes require another workflow. The worker image is outside the editable checkout.

## Publication and delivery

Only a candidate with passing `check`, `build`, `format:check`, a reviewer-model verdict and a matching artifact hash enters publication. The trusted host publisher creates a Git tree and commit from regular-file content using the operator-configured human identity, then a deterministic branch and draft PR. It cannot force-update a ref, change workflows or publish credential paths. It reconciles a lost branch/PR response against the actual tree, base and repository; an externally changed head stops publication for inspection. Private incident prose, command output and raw traces never enter the generated public PR description. Source changes still require independent review for accidentally included private content.

The worker review is a recorded report, not authority to merge. The public PR explicitly requires CI and independent approval of its published exact head under REVIEW.md. This milestone does not merge or deploy runtime-created PRs. Once publication has started, cancellation is refused until the uncertain/in-flight write is reconciled. Completed PRs are retained. A failed publication remains inspectable and is reconciled by later ticks rather than creating a second PR.

Milestone updates and questions use an outbox. A send with unknown outcome becomes `uncertain`; restart recovery does not resend it. Owner status reads preserve the underlying result. Messages are bounded for Telegram. Host routing sends validated milestones to Coding and requirement briefs/decisions, questions, pauses/failures and completed PRs to General. The original job thread remains stored; model text cannot choose a delivery target. Revoked owners cannot use worker APIs or receive updates.

## Operator activation

The default is off. The code and migration can ship before provider activation. Live sandbox execution additionally requires all of these reviewed setup steps:

1. Run normal checks and obtain exact-head independent review. Install additive migration 024 and the changed Compose baseline through the reviewed operator rollout (`scripts/deploy-coding.py`). Preserve existing tables, pending approvals and paused work. The normal release guard refuses DB/Compose differences and must stay intact.
2. Run the main-only `coding-worker-image` workflow. Make the resulting GHCR package public for the uncredentialled sandbox image pull. Record its exact digest in `config/coding.json` through a reviewed PR. Tags are insufficient. CI builds the same Dockerfile and checks the non-root runtime and installed tools.
3. Provision the dedicated project using `deploy/coding/codebuild.json` in Singapore. Its role has no identity policies; it can assume only for this project's source ARN/account. It has no production access, logs, source integration, privileged mode or injected environment secrets. Do not reuse a project with credentials or extra permissions. The controller's separate identity receives only the reviewed project operations in `controller-policy.json`, plus PassRole for the exact policy-free worker role with a CodeBuild service condition. Replace `ACCOUNT_ID` and `WORKER_ROLE_NAME` using the actual stack outputs. AWS authorises BatchGetBuilds and StopBuild against the project ARN, not a build ARN; see [the service authorisation contract](https://docs.aws.amazon.com/service-authorization/latest/reference/list_codebuild.html). Region, compute availability and first image pull need live verification.
4. Create and install a GitHub App on Chief's repository only, with Contents and Pull requests write and Metadata read; no Actions, Workflows, Administration or deployment permissions. Put the App ID, installation ID and private key only in the host's private environment. Never give the sandbox that key or token. Configure the human commit name/email. GitHub App permissions do not enforce branch restrictions: the publisher enforces its own deterministic branch path and never writes main.
5. Generate a host-only authentication key and configure the `CODING_*` environment names from `.env.example`, the scoped AWS identity and public HTTPS origin. Install `deploy/coding/Caddy.routes` within the existing site only after authentication tests pass. Preserve all other ingress routes, TLS storage and denied paths; do not expose port 3000 or enable access/body logs.
6. Enable `CODING_RUNTIME=on` during an idle reviewed rollout. Startup checks migration, required configuration, image digest and the dedicated provider project. Verify unauthenticated worker endpoints return 401 and unknown paths 404. Run one explicitly requested sandbox plan, then one bounded synthetic bug through checks, review and a draft PR; confirm cleanup reaches complete. Keep paid model/provider acceptance distinct from mocked tests.

If AWS or GitHub App access is unavailable, preserve the tested PR and record the exact setup boundary. Do not copy broad credentials from the developer machine or expand an existing log-reader identity.

Rollback: turn the runtime off only once active sandboxes have been terminated/reconciled, then restore the prior app image if needed. Retain additive coding tables, checkpoints, PRs and immutable image digests. Disabling controller ticks while sandboxes run prevents cleanup, so inspect them first. No down migration, data reset, task replay or credential export is part of rollback.
