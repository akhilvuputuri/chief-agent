# 162 — Which published advisories reach Chief, and which can be fixed without a major upgrade?

Work date: 2026-11-11. Written: 2026-11-11.
Status: tested; release pending. Six packages are updated within their ranges. Three findings stay open, each named below: zod (fixed only in 4.x), minimatch (fixed only in 11.x) and the copy of undici that `pi-coding-agent` 1.1.0 pins. A worker image built from this change moves only the worker's model calls to undici 8.12.4; its other requests keep going through the pinned 8.10.2 copy.

## User-visible problem and preceding iteration

No incident is recorded. A query of the OSV database on 10 November (reported) listed published advisories against eight packages in the two lockfiles, six of them rated high (four in undici, one each in body-parser and zod), and nobody had checked whether Chief's code reaches the affected paths.

Earlier dependency work: [journal 126](126-fetch-hygiene-and-node.md) pinned Node 22.23.4 for its bundled undici, [journal 127](127-closing-dependency-hardening.md) closed #329, and [journal 156](156-room-for-the-whole-plan.md) made undici 8 a direct dependency of the Pi runtime.

## Evidence

Before the change the root lockfile had nine flagged versions and the Pi lockfile two; the list matched the 10 November report.

Node's own `fetch`, which the gateway uses throughout, runs the undici bundled with Node 22.23.4: 6.29.1 (measured, `process.versions.undici`), the release that fixes these advisories in the 6.x line.

**Measured, 11 November, after the change: which undici the worker's built-in `fetch` uses.** Importing the built Pi runtime in a fresh Node 22.23.4 process left `Symbol.for("undici.globalDispatcher.2")` holding an `Agent` from the 8.10.2 copy, and `.1`, the one Node 22's `fetch` reads (reviewer's test), holding that copy's wrapper around it. `pi-coding-agent`'s index loads its `http-dispatcher.js`, which imports undici, before Chief's `model.js` loads 8.12.4, and undici installs a default dispatcher only when none is set. So the first copy loaded serves every built-in `fetch` in the worker; only `patientFetch`, which passes its own dispatcher, uses 8.12.4. This was the same before the change, when there was one copy.

**Measured: zod 3.25.76 on an oversized array, 11 November, Node 22.23.4, a Mac.** The schema was an object holding an array of strict objects with `.max(2048)`, the shape of the worker's model request. The body was a JSON array of `0`, sized to a body limit. zod checks every element even when the array is over its maximum, and keeps one issue per element.

| Body size | Where Chief allows it                          | Elements | Parse time | Heap growth |
| --------: | ---------------------------------------------- | -------: | ---------: | ----------: |
|    120 kB | the gateway's default, including public routes |   59,992 |      36 ms |       22 MB |
|    400 kB | box events                                     |  199,992 |      87 ms |       62 MB |
|      4 MB | a worker's model request                       |      2 M |      1.0 s |      577 MB |
|      8 MB | other worker routes                            |      4 M |      2.6 s |     1.10 GB |

The same 4 MB and 8 MB bodies on zod 4.6.7, installed in a scratch directory, returned one issue in 2 ms with no heap growth.

Bodies over 400 kB are allowed only on coding worker routes. zod parses them only after the job's bearer token is checked. Checkpoint and finish check the token before reading the body; the other worker routes read and JSON-parse up to 8 MB first. Checkpoint and finish uploads go up to 64 MB and were not measured. Whether a command the coding model runs in its sandbox can read that token was not traced. The production host's free memory was not read.

## Diagnosis and alternatives

- **Fixed inside the declared ranges:** body-parser, qs, ip-address, both fast-uri copies and fastify. `kite update` takes the newest version each range allows, so fastify went to 5.12.8 rather than 5.12.6 and qs to 6.17.1 rather than 6.16.1. fastify 5.12.8 requires find-my-way 9.10.0, which brought ret 0.5.1 and safe-regex2 5.1.2.
- **undici 8.12.4, not 8.12.2.** OSV names 8.12.2 as the fixed version. undici's release notes for 8.12.4 (5 November) list six more advisories against 8.12.2 and 8.12.3, one of them high (GHSA-mqg3-3v4r-cm32, cache poisoning across a redirect chain). The query by npm package and version returned none of them for 8.12.2 or 8.12.3 on 11 November: OSV holds the high one as CVE-2026-116592 with a Git range naming v8.12.2 and v8.12.3 and no npm range. Reported by upstream, not checked against the code.
- **`pi-coding-agent`'s copy of undici stays at 8.10.2.** Version 1.1.0 pins `undici` to exactly 8.10.2, so raising the Pi runtime's own pin leaves that package its own copy, and that copy stays the worker's default dispatcher. Kite refuses `overrides` in `package.json`, so the pin cannot be overruled from here. `pi-coding-agent` 1.5.0 and later pin undici 8.12.3 and minimatch 11.0.3; 8.12.3 is one of the versions the 8.12.4 notes name. Setting the default dispatcher from the 8.12.4 copy when the Pi runtime starts would move the worker's other requests as well; that is a source change to the coding harness and was not made.
- **zod has no 3.x fix.** 3.25.76 (July 2025) is the last 3.x release; the advisory is fixed in 4.6.6. Moving 68 importing files to zod 4 is a major upgrade and was not attempted. A length check before zod on the worker routes would bound the measured growth without the upgrade; not built.
- **minimatch is fixed only in 11.0.1.** It is not a dependency Chief declares; it arrives with `pi-coding-agent`, and changes only by upgrading that package from 1.1.0 to 1.5.x, four minor releases of the coding harness that have not been evaluated here. Not attempted.

## Implementation and review

- `coding_runtime_pi/package.json`: `undici` 8.10.2 → 8.12.4.
- `coding_runtime_pi/package-lock.json`: `node_modules/undici` 8.12.4, and `pi-coding-agent`'s nested 8.10.2.
- `package-lock.json`: body-parser 2.4.0, qs 6.17.1, ip-address 10.7.6, fast-uri 3.1.9 and 4.2.3, fastify 5.12.8, find-my-way 9.10.0, ret 0.5.1, safe-regex2 5.1.2, and undici 8.12.4 under `coding_runtime_pi`, with 8.10.2 kept at the top level for `pi-coding-agent`. The worker image installs from this lockfile (`Dockerfile.coding-pi`).
- No source change, no database or Compose change.

All versions were changed with Kite (`kite update …` in the root, `kite install undici@8.12.4 -E` in the Pi runtime). Kite sorted the Pi runtime's dependency keys; the original order was restored by hand and Kite kept the lockfile unchanged.

**Independent review (Claude Opus 5.5), 11 November, on `74940ba`: changes requested, all in the records.** It checked every entry of both lockfiles by script and found the ranges satisfied and nothing unrelated changed. It found this entry wrong about undici: the first version said `pi-coding-agent`'s copy was never used to dispatch, when that copy is the worker's default dispatcher. Checking that correction found the worker also calls GitHub's API through it, not only the gateway. The review also corrected the count of high advisories (six, not four), the wording about when large worker bodies are authenticated, and the statement that OSV did not hold the 8.12.4 advisories. All four are corrected above.

## Verification and outcome

- **Measured after the change:** the same OSV query flags three versions in the root lockfile (undici 8.10.2, zod 3.25.76, minimatch 10.2.6) and two in the Pi lockfile (`pi-coding-agent`'s undici 8.10.2, minimatch 10.2.6), down from nine and two.
- **Tested, 11 November, a Mac on Node 22.23.4:** after a clean `kite ci`, `kite run check` exited 0 in 6 min 19 s with no failing test, and `kite run format:check` passed. The Pi runtime's 123 tests, which include the patient-fetch tests, ran on undici 8.12.4.
- **Not verified:** the gateway under real traffic on fastify 5.12.8, and a worker's model call on undici 8.12.4. Workers run the pinned image built from `fa058f9`, which has undici 8.10.2 throughout. fastify's and find-my-way's changelogs between the old and new versions were not read; the test run is the only evidence for them.

- Owner decisions: upgrade `pi-coding-agent` to 1.5.x (minimatch 11.0.3, and undici 8.12.3 in place of 8.10.2, still behind 8.12.4) or set the worker's default dispatcher from the 8.12.4 copy; and either move to zod 4 or add a length check ahead of zod on the worker routes.
