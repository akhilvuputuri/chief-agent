# Owner confirmed responsibilities

Released for [issue 131](https://github.com/akhilvuputuri/chief-agent/issues/131) as [v0.3.32](https://github.com/akhilvuputuri/chief-agent/releases/tag/v0.3.32), verified at `9f5031ccb3a45e54cdde7f3f41accaa498faceff` on 2 October 2026 SGT. Migration 023 is installed and production has `RESPONSIBILITIES=on`; the source default remains off. No responsibility was created during rollout. Explicit Telegram confirmation starts monitoring. Live Telegram/provider acceptance remains separate; see [release evidence](journey/54-responsibilities.md#release-closure).

The owner can ask Chief to keep watching an ongoing concern. Chief resolves the exact subjects and sources, proposes a self-contained specification, and sends a Telegram confirmation card. Monitoring begins only after the owner confirms that exact card. A new specification needs another confirmation and creates an immutable revision. Background work and source content cannot activate or widen monitoring.

## Behaviour and initial policy

`responsibility_create`, `responsibility_list`, `responsibility_update` and `responsibility_history` form the management surface. Lifecycle changes are foreground-only; edit uses an exact base revision. Pause and cancel stop later checks, tool dispatch and pending notifications. Already-started actions can finish and remain recorded. Resume re-enables checks but never resumes a paused investigation automatically; the owner selects its exact task with `/continue`, or cancels it. An old revision's task cannot be continued under a newer specification.

One responsibility has one outcome with explicitly declared supporting sources. Parcel IDs are fixed, not whatever is currently active in conversation. The initial tools support query-scoped Gmail, applied parcel changes, qualifying primary-Calendar meeting instances and ScheduleParser schedules. No new stock/news poller migration, carrier integration or broad mailbox synchronization is included.

Default allocation is 6 investigations per concern and 25 per owner per Singapore calendar day. An investigation begins with 5 active minutes, 10 model calls and 30 tool calls. Model-backed public searches also consume that investigation's model allocation. Explicit `/continue` uses the existing owner-authorized additional allocation; it does not replay completed work. Reported provider charges and estimated unreported charges remain distinguishable. No dollar cap is added.

Default quiet hours are 23:00–08:00 SGT; equal endpoints disable quiet hours. Optional monitoring windows reuse the stock window calculation and are separate from quiet hours. Delivery can be set to an exact daily Singapore-time slot. Otherwise deferred findings use an 08:00 digest. Initial interrupt caps are 3 per concern and 8 across responsibilities per owner/day. They do not alter existing news/stock policy. Every default is displayed before confirmation.

An optional owner-confirmed `urgentWhen` criterion lets an interpreted action requirement bypass the daily delivery slot. Email urgency still respects quiet hours. A watched meeting starting within two hours is the deterministic time-critical rule that can bypass both the slot and quiet hours. Calendar `internalDomains` defines organization domains to exclude; an explicitly empty list means any non-owner, non-resource attendee.

## Changes and investigations

Source checks are deterministic and have no model dependency. Checks commit admitted candidates and cursor advancement together. A unique source key per concern revision prevents duplicate admission across restarts. Inbox entries stay pending when an investigation is running, paused or out of daily capacity. Each launched task has a frozen bounded batch; later events wait for the next batch instead of mutating an in-flight prompt. Different concerns share the existing background worker. Expiry is enforced before checks, launch, dispatch and delivery; queued work is paused when its period ends. Sweeps query closure-eligible allowed concerns before applying their bounded limit.

Investigations use only the saved specification, exact candidates, current watched records and up to three prior findings from that revision. Rolling conversation, unrelated memories, recent feeds and pending approvals are not model context. The dispatcher enforces the scope even if an injected source requests another tool. Dynamic tool loading, conversation lookup and delegation are unavailable in these investigations.

Reads are restricted to admitted Gmail message IDs and watched parcel IDs. Public research is available for explicitly scheduled research. The only unattended domain write is an email-derived observation on an existing watched parcel: no parcel creation, archive/reopen, owner provenance or unrelated writes. The Gmail read receipt must establish its message and Date header; mailbox identity is pinned and checked again. Parcel precedence and matching rules remain those in [deliveries](deliveries.md).

Calendar creation, deletions, library writes and skill activation cannot run unattended from this surface. A finding can propose an action; the owner requests it in the foreground and the existing Telegram approval boundary remains authoritative. A responsibility is never approval.

The model saves `responsibility_report` after investigation work. Findings include what changed, why it matters, a current understanding, evidence keys, an optional next action, a stable substantive fact key and proposed attention. First-match completion additionally needs a substantive, relevant finding with verified references and an explicit resolved proposal; mere candidate admission or an unchanged/irrelevant result never closes it. This semantic interpretation remains model-proposed, not independently certified. The host accepts the report for attention only after normal runtime completion. Missing reports, failed or budget-paused work stay inspectable and produce one policy-controlled intervention notice per task. A completed report/outbox gap is recoverable with local database work, never another model or tool execution.

## Source adapters

**Gmail:** one bounded IDs-only list page per check; bodies are read only during investigation. The existing read-only client and request allocation are reused. Poll the confirmed mailbox and query at 30 minutes by default, configurable 15–240 minutes. A fixed scan end and page token survive partial scans; the completed watermark advances only after all pages are accounted for. A five-minute overlap plus durable ID deduplication covers ordinary boundary arrivals. Activation starts from now. This is not a guarantee against arbitrary provider indexing delay or backdated imported messages; history exposes completed and incomplete coverage. No mailbox index, history synchronization or push subscription is installed.

**Parcels:** database triggers record meaningful status, ETA, carrier wording or archive transitions atomically with parcel writes. Events retain the producing run, so a concern's own parcel write cannot recursively investigate itself. Another explicit concern may observe the change. Stale observations that do not change the parcel emit no event.

**Calendar:** a monitoring-only projection reads attendees and recurrence identity, expands recurring instances and follows up to five bounded pages. Incomplete attendee/page coverage degrades the check rather than claiming absence. The host filters qualifying timed meetings and admits one key per stable occurrence per revision. Each occurrence gets its own investigation so cancelling one cannot discard another meeting's preparation. Delivery rechecks that the event still exists at the saved, future start time; moved/cancelled or elapsed meetings suppress old preparation. The ordinary conversational Calendar projection is unchanged. Polling and the shared work queue do not guarantee execution at the exact lead-time instant under backlog or exhausted allocation.

Both documented time forms are accepted: RFC3339 with offset, or an unambiguous local dateTime with an explicit valid IANA timeZone. Every timed value normalizes to the same UTC representation for recurrence and delivery comparisons. Ambiguous daylight-saving folds require a numeric offset; missing zones, malformed members and nonexistent local times degrade the check visibly rather than becoming healthy empty coverage. Normalization depends on the supplied wall date, not the current timezone offset.

**Schedule:** the due occurrence is admitted without a model. An investigation can then perform public research and compare the saved baseline. This is the deliberately disclosed U6 clarification: unchanged results are silent, but generic scheduled research can spend model budget each occurrence. Zero model usage on unchanged arbitrary topics would require a declared deterministic source; no additional provider framework is built here. Existing ScheduleParser hourly minimum and latest-only catch-up remain.

Public research uses the exact confirmed `publicQuery`; page reads must name exact URLs returned by that investigation's search. Source text cannot widen a search or add private data to an outgoing query/URL.

## Attention and delivery

Final outcomes are `now`, `briefing`, `quiet` and `drop`. History records the decision and reason, including unchanged, irrelevant, duplicate, non-actionable parcel status, quiet-hour deferral, interrupt-cap deferral, source degradation and superseded revision. Parcel notifications default to delayed, out-for-delivery, delivered or an interpreted action requirement. A deterministic end condition can close silently or send one closing message; a last parcel finding and closure are combined where possible.

Known facts use persisted identities and structured state. Generic scheduled findings also depend on the model's substantive fact key; semantic equivalence and factual interpretation are not independently certified. Delivery serializes duplicate checks and interrupt reservations per owner. Sending and uncertain attempts count toward the cap. Deferred findings form bounded digests with exact member IDs, retaining per-finding feedback and send state.

Messages carry model-written prose, evidence references and Useful / Later / Resolved / Less like this buttons. Feedback is bound to owner, sent message and current revision; each action is idempotent and serialized with delivery reservations. Later resends the saved finding at a later slot without research while the concern is active. Resolved stops that concern and suppresses outstanding notifications, including deferred reminders; later feedback cannot revive them. Less like this reduces that concern's interrupt allowance within a bounded range; it never changes global policy, source scope or investigation instructions.

Outbox state is pending → sending → sent/uncertain. A restart or ambiguous send never automatically resends it. Startup health is not notification usefulness. `/status`, tool history and authenticated read-only Mini App views show concerns, checks, findings, reasons and allocation/usage; no Mini App mutation or approval route is added. Lists prioritize active/paused concerns and provide bounded pagination for completed records. Resumption selects only prior isolated background runs, never a later foreground run bound to the same task.

Responsibility tables contain source references and bounded domain snapshots, not raw email bodies. Findings stay private in Postgres. Existing runtime tool-result storage still retains private observations; this feature does not claim that no email content is stored anywhere. Operational logging uses existing sanitized projections; private payloads are absent from public CI and journal evidence.

## Reviewed rollout and rollback

1. Review the exact PR head independently, including migration, operator script and failure scenarios. Run check, build, formatting and `python3 scripts/test-deploy-responsibilities.py`. Paid smoke/evaluation calls are not routine validation. After merge, fetch its exact commit into the trusted checkout, verify its reviewed tree, create a `git archive --format=tar SHA` and calculate its SHA256. Record/carry that digest through a trusted channel separately from the uploaded archive; do not trust a checksum supplied by an untrusted archive producer.
2. The candidate is off by default. Ordinary release refuses the database/Compose change; do not bypass it. The reviewed operator script `scripts/deploy-responsibilities.py ARCHIVE SHA TRUSTED_SHA256` accepts only baseline `aacdc2ac9d9c9a92a11f74c19d88b93daa189a35`, whose exact release receipt was observed on 2 October 2026. Its live RELEASE guard must match; reconcile and re-review a newer baseline rather than changing the guard during deployment.
3. The script locks releases, validates the independently trusted digest and the archive's commit label, and extracts the same bounded immutable bytes it hashed. The PAX label alone is not content authentication. It preserves historical migrations and private `.env`, builds first, refuses active runtime/queued input, installs only migration 023, checks startup health and publishes the exact source/RELEASE. It permits only the migration Compose entry and default-off capability field. It does not install a root-owned release handler or configure credentials.
4. Verify migration marker, exact deployed SHA, independent health and preserved-record counts. Activation is a separate explicit operator step after review: configure the non-secret `RESPONSIBILITIES=on` setting and recreate the gateway only when idle. Verify the capability and owner confirmation flow. Do not create a real monitoring concern or perform paid acceptance without an owner request.
5. Rollback restores the previous application/Compose, retains all additive tables and records, and does not reverse data or replay uncertain tasks/sends. Old application code does not execute responsibilities. Disable the capability before a later rollback/recovery; inspect paused tasks before explicit continuation.

The remaining cloud/local gap is operator-mediated schema installation and activation. Shared scripts and synthetic scenarios reproduce the feature without production credentials; a narrowly reviewed remote migration interface remains future work.
