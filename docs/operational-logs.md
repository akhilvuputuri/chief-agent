# Operational logs

The gateway writes one JSON object per stdout line for operations only. Postgres `events`, `runtime_runs` and `runtime_calls` remain the authoritative private record. These lines exist so a failed interaction can be located and correlated to its run, tool call and release without reading private content or connecting to the server. On the production host they go through journald to CloudWatch Logs.

Implementation: [src/ops-log.ts](../src/ops-log.ts), [src/process-guard.ts](../src/process-guard.ts), tests in [tests/ops-log.test.ts](../tests/ops-log.test.ts).

## Safety contract

- Each line has `schema: "chief.ops/1"`, `ts` (UTC), `level`, `event`, `service` and `release` (the deployed commit, or null).
- Only the fields listed in `ops-log.ts` are accepted. Each has a narrow shape: identifier, lower-case name, code, model ID, short provider name, non-negative number or boolean. A value outside its shape is dropped and counted in `dropped`, and unknown keys are discarded. No field accepts arbitrary text.
- Values come from structural sources: host-generated IDs, host-defined operation names, internal states, provider error codes and counts. They never come from prompts, tool arguments or results, message text, email, attachments, OAuth codes, tokens, URLs or exception messages. A tool name the model invents is logged as `unknown`. Shape checks are a second layer: they cannot tell a one-word secret from an ID, so no new field may be fed from model, user or third-party text.
- Startup refusals carry fixed codes such as `STARTUP_MIGRATION_017`. Other errors are recorded as class name, system code (for example `ECONNRESET`) and up to three `dist/` or `node:` code locations, never the message. `process-guard.ts` replaces Node's default crash output, which would print the message and stack, and then exits with code 1 as before.
- Logging is best effort. A failed write never fails or repeats the recorded action. Missing lines do not prove that nothing happened: check the heartbeat and Postgres.

The mapping from recorded events to log lines is also in `ops-log.ts`. Content-bearing event types such as `research.model_input`, `telegram.view_state` and `plugin.pinned` are never projected. Tool outcomes are logged from the call journal, not again from `tool.*` events. A failed scheduled delivery can produce two lines from different layers: a transport line (`telegram.delivery_error`) and the job's recorded state (`routine.delivery` uncertain, `daily.failed`, `work.pass_failed`). Correlate them by `runId`/`ref` rather than counting both as separate incidents. For approvals, input and view events, `ref`, `inputId` or `approvalId` identify the record because their event row is not keyed by a run.

## Adding an event

Add the event type to `projections`, or call `opsLog` at a boundary, with fields that already fit an existing shape. If a new field is needed, add it to `fields` with the narrowest shape. Extend the hostile-payload tests so they cover it. Never widen a shape to accept a message.
