# Durable invoice gathering

Implementation candidate based on freshly fetched main `591ee4af071f9128b2c56ab82feda386d2a6f77e`, incorporating released subscriptions and the Python coding foundation. No gathering release is claimed yet. Related issues: [132](https://github.com/akhilvuputuri/chief-agent/issues/132), [48](https://github.com/akhilvuputuri/chief-agent/issues/48) and [47](https://github.com/akhilvuputuri/chief-agent/issues/47).

Chief owns conversation and scope. It starts a durable collection, delegates source work to the gathering agent, and explains the actual result. The agent chooses among the requested sources in the owner's order. The host enforces assigned task/revision, exact target keys, source/mailbox/origin grants, file ownership, idempotency, recorded invoice clues and coverage checks. It uses the existing WorkWorker, budgets, explicit continuation and cancellation rules. Existing paused tasks are not resumed.

The first workflow gathers original PDF invoices from explicitly provided files, scoped Gmail PDF attachments and billing-portal links. Source order is part of the saved request. Invoice issue month and billed service month are different criteria; ambiguous periods require clarification. For example, [DigitalOcean documents](https://docs.digitalocean.com/platform/billing/invoices/) that the prior month's usage is invoiced on the first day of the following month. [Claude's API invoice guidance](https://support.claude.com/en/articles/16608069-understanding-your-claude-api-invoices) identifies Console invoice history and downloadable/viewable invoices. Portal controls are observed, not guessed from fixed CSS selectors. OpenAI plan/workspace invoice availability is role-dependent ([official documentation](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-usage-and-cost)); no consumer billing deep link is assumed.

## Files and coverage

Additive migration 028 stores owner-scoped collections, scope revisions, attempts, candidates, matches, browser state and encrypted PDF artifacts. Original bytes are AES-256-GCM encrypted with owner/hash-bound associated data; typed invoice clues cross the model/history boundary instead of full document text. Original file bytes are preserved; public metadata uses generated names. The key stays on the production host. This protects database copies, not a compromised application host. PDFs may contain private billing details; original files and browser sessions never enter public telemetry, Git, model memory or trace JSON.

A matching file is separate from checked coverage. Provided-file coverage requires inspecting the explicit inputs. Email coverage requires complete scoped PDF-search pagination in every selected mailbox and inspection/capture of the returned PDF parts. Browser coverage requires an explicit owner invoice-history count for the selected account/month and that many distinct recorded invoice identifiers; a sole matched PDF can be counted without an identifier. Byte-different variants of one numbered invoice count once, and multiple unidentified PDFs cannot establish browser invoice-history coverage. These are recorded source boundaries, not a census of unknown accounts or independent invoice authentication. Unknown, scanned, truncated or ambiguous documents remain unverified. Vendor aliases broaden search but never authorize product substitution (for example, OpenAI API is not ChatGPT). Conflicting products are refused; ambiguous shared-vendor PDFs and account-labelled targets require explicit authenticated owner target verification for each PDF, bound to its artifact and current scope revision; email mailbox identity is not billed-account evidence. The owner downloads/inspects the candidate before confirming in the Invoices view. This is the sole target-attestation write in that view, not a model tool. Gathering does not write subscription records; ledger intake remains owner-confirmed.

Files are byte-deduplicated. Collection limits are 100 stored PDFs and 200 MiB, with the existing 20 MiB PDF limit per file. Current-scope matched files can be downloaded individually or as a ZIP. Scope changes preserve prior files/receipts, revoke old browser sessions and invalidate previous coverage proofs. They require an authenticated foreground owner follow-up and the current revision.

## Browser boundary

The browser and public egress proxy run separately from the credential-bearing gateway. The browser receives only its internal control secret, scoped session commands and browser-owned authentication state. There is no model shell or arbitrary JavaScript tool. Public HTTPS destinations are resolved and pinned by the proxy; private/special networks, direct non-proxied egress, web sockets and service workers are denied. Agent navigation is confined to observed invoice links and declared origins. Automation uses a positive inventory of document routes, exact granted navigation URLs and observed scoped PDF retrieval. Every background request is frozen during automation; unknown routes and complex portals require owner control. The agent cannot submit forms.

A handoff freezes automation. A connected, authenticated owner controls the browser view for login and navigates to invoice history; the agent sees no password, input value, cookie or full page text. Page writes are enabled only while the owner control connection is live. Ending/disconnecting control restores the read-only network policy. Browser state is encrypted for the current task; retaining a login for later tasks is opt-in. Clicking Done does not resume a paused task or grant more model budget; the owner returns to Chief and explicitly continues. Browsers expire and close when idle; cancellation and expiry revoke session state. Saved profiles can be forgotten from the invoice collection list, which also closes browsers for that origin. Already captured artifacts survive restart; a resumed browser gets fresh observations instead of reusing stale link IDs.

Some sites use POST requests even for read queries or require unsupported browser features. These require owner navigation or remain blocked; no anti-detection or CAPTCHA bypass is promised. External writes, full document/spreadsheet generation and general image/OCR intake remain separate work.

Browser dependencies and sandbox configuration follow [Playwright's Docker guidance](https://playwright.dev/docs/docker). Downloads are explicitly persisted before a context closes, because [Playwright removes temporary downloads on context closure](https://playwright.dev/docs/downloads). Authentication state is treated as credential material ([Playwright guidance](https://playwright.dev/docs/auth)). Actual server sandbox validation, full review, [reviewed operator rollout](gathering-deployment.md) and live owner acceptance are required before calling this shipped.
