# Troubleshooting Chief

Use this page for an incident reported from Telegram, a cloud coding task, or a local checkout. It describes how to find evidence; it is not a claim that a particular integration is currently healthy. Read the relevant domain runbook and source before changing behavior.

## Sources of truth

1. GitHub `main` is the integrated code and documentation. A branch, PR, candidate section, or package version is not the deployed application.
2. The exact commit's successful release receipt and the server `RELEASE` value establish what was installed and healthy **at release time**. `npm run release:status -- FULL_SHA` checks the receipt. Use current diagnostics to check whether that is still the running SHA. Startup health does not prove a Telegram or provider workflow succeeds.
3. Owner-scoped Postgres runs, events, calls, approvals, source records and message history establish what happened in an interaction. A model's reply or a screenshot alone does not prove a tool call, approval, or external write succeeded.
4. `docs/current-work.md` records the latest verified milestone and open work; `docs/journey/` preserves dated decisions and incidents. Historical reports remain historical even when a later fix shipped. If evidence conflicts, record the discrepancy and update the docs after verifying the live state.

Never put API keys, OAuth tokens, raw mail, private conversation text, attachment contents, or full production traces in Git, PRs, Actions output, or an agent prompt. Use structural metadata and anonymized regression fixtures. See [security](security.md).

## First pass from any coding environment

1. Record the user's approximate Singapore time, requested action, Telegram result, and whether a button was shown or pressed. Keep private details in the authorized task, not an issue. Identify the relevant source module and existing incident or issue.
2. Run `npm run doctor:cloud` in the **actual** coding session when GitHub or production evidence is needed. Repository read, Actions read, workflow dispatch, merge and production access are distinct capabilities.
3. Fetch `main`, identify its SHA, and verify the corresponding release receipt. Do not infer that the running server matches `main` from a passing PR check.
4. If authorized, run the manual `production-diagnostics` Actions workflow and read its completed output. If workflow dispatch is unavailable, the repository owner or the installed Devin GitHub bot can post exactly `/companion diagnose` on a repository issue or PR. Other actors cannot trigger that path. See [cloud-agent workflow](cloud-agent-workflow.md) and [cloud development](cloud-development.md).
5. Match timestamps and run IDs before attributing an aggregate or failure to the reported request. If evidence is unavailable, state which read was denied and what remains unknown. Do not turn an unverified token, deployment, or model explanation into a diagnosis.

The restricted Actions command calls only the root-owned `diagnose` entrypoint. It reports the server release, last 15 run states, bounded model failures, 24-hour tool outcomes/costs, and selected conversation-routing/context aggregates. It does **not** expose exact tool arguments/results, approval rows, Google responses, raw gateway logs, or conversations. The trusted server entrypoint in [cloud-release.py](../scripts/cloud-release.py) is installed separately from ordinary app code; a repository edit alone does not update its live output. A local operator may have a separate connection for narrow private inspection. Cloud tasks do not inherit that connection or browser sessions. Do not copy the operator credential or broaden the restricted SSH command to make debugging convenient.

## Calendar event incident

Follow [Calendar's execution and recovery contract](calendar-approval.md) in this order:

1. Did `calendar_draft` run and save an owner-scoped `calendar_create` approval? If not, inspect the model/tool failure or missing event details; no event was requested from Google.
2. Was the pending approval preview delivered with **Approve event** and **Decline**? A saved draft alone is not a delivered card. If no card appeared, inspect the Telegram delivery path before changing Calendar credentials.
3. Was the exact button clicked before its 15-minute expiry? Natural-language “yes” does not approve. Check the approval state and `calendar.approval_decided` event.
4. If approved, check for `calendar.created` and its receipt, or a definite pre-send `failed` result with `failure.code` and `calendar.not_sent`. Only an uncertain post-attempt outcome requires **Check status** or authorized operator inspection by the deterministic event ID; never issue a second POST or reset the approval to pending.
5. For a definite `authorization` or `configuration` failure, check the expected Google account, refresh-token validity, client settings and granted write scope privately. A successful Calendar list query does not prove the separately consented write scope is present. The repo documents the setup procedure, **not** the current secret value or an independently verified current write-token status.

The current bounded Actions diagnostics cannot identify the exact approval or Google failure for one event. Their `calendar_draft` operation counts can narrow a window, not establish the outcome of a specific request. Current source records bounded categories for definite pre-send failures; a possibly sent insert remains uncertain without a provider category. Until a scoped private incident-trace reader exists under [issue #28](https://github.com/akhilvuputuri/chief-agent/issues/28), use an authorized local operator inspection or user-provided Telegram result and report the remaining uncertainty. Do not add raw Calendar content to the public diagnostic output. Check the exact deployed SHA before assuming live behavior matches current source.

## Close the loop

Turn a reproduced failure into a focused regression fixture. Record the observation, diagnosis, change, tests, independent review when behavior changes, exact release evidence, and live acceptance limit in the relevant [journal entry](journey/README.md). Update `docs/current-work.md` and the domain runbook. If access or consent is missing, document the concrete blocker and next safe check; do not mark the integration fixed.
