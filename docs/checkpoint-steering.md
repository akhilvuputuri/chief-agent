# Steering a running conversation at checkpoints

Candidate v0.3.9 on `feature/checkpoint-steering` builds on released v0.3.8 at `d0e33365c7cec7b7cb1eb64c22de7c09d5d9a314`. This document describes the candidate, its required migration and the remaining release checks. It does not claim that v0.3.9 is deployed. The earlier [rolling-conversation design](rolling-conversation.md) remains the foundation for protected context, original-message retrieval and independently selected jobs.

## Input and execution

Ordinary input no longer aborts an in-flight model request. Telegram records each input and its message/reply/update identifiers immediately. Photos, PDFs and voice notes enter a preparation queue with two concurrent preparations per user; text does not occupy a preparation slot. Preparation can overlap active execution and speech delivery. The foreground inbox consumes ready inputs in their recorded order, waiting when an earlier input still needs preparation. A failed preparation becomes terminal and unblocks later input.

After a model response or an already-dispatched tool finishes, the loop checkpoints its complete result. Before dispatching another tool, starting another model request or delivering a reply, it checks for newer input. Remaining calls from the old model batch receive `NOT_DISPATCHED` observations. A journal entry created before an authorization await is closed as interrupted if the call never reaches its dispatcher. Completed writes and uncertain-write protections retain their existing behavior; steering does not retry a write.

An unbound foreground run drains the ready inputs, appends each as a separate ordered user message, refreshes context and continues under the **same run and allocation**. Each input has its owning run, consumption time and exact message index; `input.checkpointed` links these references without copying message text. Current images remain available in memory across these checkpoints. PDFs retain owner-scoped extracted sources; raw image and audio bytes are not stored in history or traces.

If work tools have bound the foreground run to a durable task, newer input causes a handoff at the next checkpoint. The old task pauses with its completed state; queued input begins an unbound foreground run. It does not inherit the task's checkpoint, automatically resume it or authorize skipped actions. Explicit `/continue <id>` remains the way to grant the selected job another allocation. When that job resumes, run-history selection starts at its earliest durable input message index rather than searching for matching text, so repeated identical follow-ups cannot move the task's history anchor. Earlier migration013 inputs without an index retain bounded history without guessing an anchor from message text.

Read-only research, media and job-alignment children inherit the parent's cooperative yield signal. Their in-flight model/read can finish; subsequent calls stop at the checkpoint. An incomplete result includes exact owner-scoped `observedSources` references for successful source reads, plus the child run and stop reason. This is partial evidence, not a validated complete report. A media interruption leaves current attachments available to the parent for the revised question.

## Cancellation, delivery and reset

`/cancel` and `/workcancel` remain explicit cancellation: they abort the active model request and prevent later dispatch. An already-started tool may finish and retain its result. Cancellation also invalidates pending delivery for the current run after model execution has finished. Job-specific cancellation remains scoped to the selected job.

The complete model-response journal is immutable. Owner/run/message-index entries in `run_message_context_exclusions` durably exclude superseded final assistant text from subsequent model context, including a later granted task resume in a fresh process. The rolling conversation also omits those finals; tool-call/result groups remain recorded. Telegram-managed final candidates and their pending-delivery exclusions commit in the same checkpoint statement; a restart between checkpoint and later tracing cannot expose the undelivered final. Recording delivery releases only pending-delivery exclusions; a superseded occurrence stays excluded even if another reply with identical text was delivered. The original payload and occurrence remain available for journal inspection. For Telegram-managed final delivery, conversation references start as `pending` and become `sent` only after successful delivery. History loading, search and reads exclude pending replies, so a withheld or failed final reply does not look like something the user saw. Existing historical entries retain `recorded` status; the migration does not invent prior delivery receipts. A successful send followed by a failed recording operation can conservatively leave a pending entry; there is no automatic resend.

Delivery checks the input revision again before sending, including around speech preparation and view rendering. It revalidates the local inbox version and cancellation after the database read, so an input or cancellation during that read cannot use a stale result. Cancelling a selected task also fences that task's unfinished delivery without suppressing an unrelated task's output. Newer input suppresses stale text or speech that has not been dispatched. `/reset` serializes its deletion after the prior foreground run's conversation commit, so that commit cannot recreate the conversation after reset. Run journals and saved domain records retain the existing reset semantics.

A Telegram send already dispatched cannot be recalled by a later guard. There is no debounce delay or guarantee that an earlier reply will be withheld if the next input arrives after its send began. These are checkpoint and dispatch guarantees, not cancellation of external operations already in progress.

## Budgets and recovery

Time/model/tool allocations and provider price ceilings are unchanged. Waiting for earlier attachment or voice preparation occurs outside active model/tool timing. Input arriving during an unbound run does not create another allocation. If that run exhausts its budget, is cancelled or fails, queued inputs are retained in terminal failed state with a parked reason rather than silently starting free replacement runs. The user can inspect saved results and resend when ready. Already consumed inputs retain their run/message references.

Startup continues to fail queued/running inputs and pause active durable work conservatively. It never replays the inbox, resumes paused tasks, reconstructs ephemeral image/audio bytes or retries uncertain writes. There is no automatic replay worker, new spending cap, new infrastructure or new authority to send email or create unapproved Calendar events.

## Inspection and verification

The diagnostics update adds bounded aggregates for steering event counts, input preparation/state, intake-to-start and intake-to-consumption delay, preparation-ready delay, conversation delivery states and journaled `NOT_DISPATCHED` calls. It reports identifiers, states, counts and times. It does not export input text, transcripts, raw bytes, source content, credentials or full model traces. Synthetic unstarted calls without a `runtime_calls` row are visible in the run journal; the journaled-call aggregate intentionally counts only created call records.

Relevant events include `telegram.input_received`, `telegram.input_ready`, `conversation.inputs_consumed`, `input.checkpointed`, `conversation.task_handoff`, `conversation.inputs_parked`, `conversation.delivery_withheld` and `conversation.delivery_cancelled`. Input and source IDs establish provenance; they do not prove that a model interpreted an instruction or source correctly.

The candidate's focused mocked checks cover model completion without ordinary-input abort, ordered same-run consumption, completed writes followed by skipped calls, journal and authorization races, suppressed final replies, final-approval lookup races, explicit cancellation, bound-task handoff, refreshed context/images and partial child source references. Existing runtime, research, media and delegation-accounting tests also passed during implementation. The operator script also passed eight offline mocked scenarios covering baseline/archive/migration rejection, busy-work/input refusal, successful rollout and startup rollback; the five new diagnostic aggregates ran against migrated synthetic PGlite data without returning message text or owner identifiers. Full integration checks, exact-head independent Astra approval, CI and rollout verification remain required. Review follow-up checks also recreate the Assistant before task grant/resume, verify pending versus superseded occurrence handling and retain the original journal payloads. No paid smoke or model evaluation was run for this change; no comparative latency, cost or answer-quality improvement is claimed.

## Reviewed migration and deployment

Migration `014_checkpoint_steering.sql` adds input preparation, consumption time and message-index fields, an input lookup index, conversation delivery state and the owner-scoped `run_message_context_exclusions` table. The latter references an existing run-message occurrence and stores only its exclusion reason and creation/release timestamps. It preserves existing payloads, message references, tasks, budgets, approvals and sources. Existing inputs default to ready and historical conversation entries default to recorded. The gateway refuses to start without migration014; Compose includes it in the explicit migration list. Earlier migration files must remain byte-for-byte unchanged.

It checks the archive's embedded commit, rejects unsafe paths and environment files, rejects changed historical migrations and permits only migration014 as new SQL. A different live release requires reconciliation and renewed review, not bypassing the baseline check.
4. The script builds before downtime and refuses running runtime work or queued/running conversation input. Wait until preparation and work finish; do not cancel user work to deploy. Verify the deployed SHA, health, migration marker and preserved domain/history counts separately. Until those checks succeed, describe this as a candidate.
