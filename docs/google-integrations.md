# Google integrations

Gmail, Calendar and both Sheet mirrors are connected in the existing personal deployment. They are called directly through validated TypeScript tools. Credentials remain outside Git. Google project and OAuth client display names may retain the original prototype name; those are existing connection identities, not runtime dependencies.

## Read-only Gmail and Calendar

> **Update, 22 November 2026:** Phase 1 of the email-search redesign changes what the three read tools return; see the note at the end of this section. The paragraphs below describe the state before it.

`gmail_search`, `gmail_thread` and `gmail_read` expose bounded message results; no send, delete, label or attachment operation exists. Search accepts Gmail's own operator syntax, returns at most ten hits and, for each, fetches `format=metadata` limited to From, To, Subject and Date, so one call yields sender, subject, date, a snippet and an unread flag instead of bare identifiers. Sender and recipient are capped at 120 characters, subject at 160, snippet at 120 and date at 40. Because those caps bound source text rather than JSON, and quote-dense content can double under escaping, the assembled result is then trimmed entry by entry until it serialises below 11,000 characters, counting what was dropped in `omitted`; the page token is bounded at 1,000. This keeps every result under the 12,000-character model projection, above which a result is replaced by a bare excerpt. The untrusted-content warning and the hint are the first fields regardless, so they survive even an excerpt. A hit whose metadata fetch fails or exceeds the turn budget keeps its identifiers and carries a `detail` note rather than failing the search. A computed `hint` asks for a narrower query above 50 estimated matches and suggests widening when nothing matched; it is never written by the model. Metadata is not a parts listing, so no attachment flag is returned; `has:attachment` remains available as a search operator. Identical searches by the same owner are served from a five-minute in-process cache.

`gmail_thread` reads one conversation oldest first, at most 12 messages, 2,500 characters per message and 6,000 characters of body text in total, reporting which messages were truncated or omitted. Every message consumes at least one character of that total, so a conversation of messages with no plain-text part is bounded by the message count rather than growing without limit. A conversation whose full form exceeds the two-megabyte response guard degrades to its message list with sender, subject and date, so the model can fall back to `gmail_read` on a specific message instead of losing the call. A message with no plain-text part is marked `bodyless`, since `gmail_read` cannot return more for it than the snippet already shown, and `truncated` means only that a plain-text body was cut. `gmail_read` still returns one message up to 16,000 characters, which can itself exceed the projection limit and be excerpted. HTML parts and attachments are never fetched or executed in any of the three. `calendar_list` reads the primary calendar with bounded time ranges. Each adapter checks the configured owner before network access. Email and event content may enter model context and is untrusted data.

> **Update, 22 November 2026 (email-search redesign, Phase 1):** Chief failed to find monthly receipt emails that were in the mailbox, and the cause was in these tools rather than in Gmail's index: HTML-only mail (most receipts) was reduced to Gmail's snippet and marked `bodyless`, search stopped at ten hits for eleven requests, threads were cut to 2,500 characters per message and 6,000 in total, and `gmail_read` advertised 16,000 characters while the projection cut it to 8,000. Now:
>
> - **Body text.** `gmail_thread` and `gmail_read` return the plain-text part when it has content, otherwise the HTML part converted to text with the mail index's own conversion (`cleanText`, including the quoted-reply cut). Such a message carries `fromHtml`; `bodyless` means a message has neither part, and its snippet (at most 200 characters) stands in. HTML is converted to text only: never executed, and no link, image or attachment is fetched.
> - **Sizes.** `gmail_read` returns up to 20,000 characters of one message, with `truncated`, `nextOffset` and `totalChars` and an `offset` argument to continue. With `messageIds` (1 to 25) it reads several messages in one call, at most four requests at a time, sharing 50,000 characters fairly, with a per-message `truncated` flag and `nextOffset`, and a failed or unaffordable message reports a `detail` instead of failing the rest. A `messageId` read keeps its earlier result shape (new optional fields only); responsibility investigations still read one confirmed message per call. `gmail_thread` returns at most 50 messages, up to 20,000 characters each and 50,000 in total, shared fairly; the metadata fallback for a conversation past the two-megabyte guard now lists 50 messages.
> - **Projection.** `src/observations.ts` keeps per-operation limits: for `gmail_search`, `gmail_thread` and `gmail_read` a payload field may be 20,000 characters and the serialised result 110,000 before it is excerpted; every other tool keeps 8,000 and 12,000. The adapter shortens the longest text (then drops trailing entries) until a result serialises below 108,000, so the untrusted-content warning stays the first field.
> - **Search.** `pageSize` defaults to 20 and may be 1 to 50. The page's metadata comes from one Gmail batch request; a failed batch, or a part it did not answer, falls back to single fetches, and an unaffordable or failed row still degrades to identifiers with a `detail`. Each row adds `received` (Gmail's `internalDate` in Singapore time), `category` (primary, social, promotions, updates, forums) and `folder` (inbox, archived, sent, spam, trash). Calendar dates in `after:`, `before:`, `older:` and `newer:` (Gmail reads them as midnight Pacific time) are sent as epoch seconds at Singapore midnight, `older:`/`newer:` as `before:`/`after:`; relative forms, numeric values and quoted text are left alone, `query` echoes what was sent and `requestedQuery` what was asked. An empty page returns a `hint` on how to broaden; a page with a `nextPageToken` says to follow it. Gathering, mail recall's keyword searches, the daily briefing and the mail-recall eval pass `pageSize: 10`, and gathering also keeps its query text unrewritten.
> - **Budget.** The per-run Gmail budget is 200 requests, a batch counting once: a backstop against runaway loops and the shared per-user Gmail quota, not a steering limit. A search costs two requests (list and batch).
> - **Unchanged.** Gmail stays read-only, owner-only, identity-checked per mailbox with no fallback to the other one, IDs are validated before any URL, requests refuse redirects, the 2 MB and 29 MB response guards and MIME part limits stand, and the warning leads every result.

Use `scripts/connect-gmail.mjs` and `scripts/connect-calendar.mjs` with a private desktop OAuth client JSON, output path and expected email. The loopback flows use state/PKCE, verify scopes/account identity and write private token files. Set the corresponding variables from `.env.example`; never print token files. Testing-mode OAuth grants may require reconnection.

## Sheets as viewing surfaces

Postgres is authoritative. Preparation uses Target roles / Preparation gaps / Preparation tasks. Daily use has Tasks / Notes / Schedules. Managed tabs are one-way mirrors: edits to them are overwritten on sync. The model cannot target arbitrary spreadsheets.

Use `scripts/connect-sheets.mjs` for `drive.file` plus identity authorization and `scripts/create-preparation-sheet.mjs` to provision the preparation workbook. Existing installations should reuse their configured workbook IDs. `sheet_sync` and `daily_sync` report actual results; database writes remain saved if sync fails. Cells use literal values to prevent formula execution. There is no durable Sheets synchronization outbox yet.

See [preparation setup](preparation.md), [daily assistant](daily-assistant.md) and [verification](verification.md) for limits and tested behavior. Existing grants do not permit email sending or calendar event creation.
