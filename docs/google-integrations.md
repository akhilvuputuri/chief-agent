# Google integrations

Gmail, Calendar and both Sheet mirrors are connected in the existing personal deployment. They are called directly through validated TypeScript tools. Credentials remain outside Git. Google project and OAuth client display names may retain the original prototype name; those are existing connection identities, not runtime dependencies.

## Read-only Gmail and Calendar

> **Update, 22 November 2026 ([journal 204](journey/204-email-search-redesign.md)):** Phase 1 of the email-search redesign changes what the three read tools return; see the note at the end of this section. The paragraphs below describe the state before it.

`gmail_search`, `gmail_thread` and `gmail_read` expose bounded message results; no send, delete, label or attachment operation exists. Search accepts Gmail's own operator syntax, returns at most ten hits and, for each, fetches `format=metadata` limited to From, To, Subject and Date, so one call yields sender, subject, date, a snippet and an unread flag instead of bare identifiers. Sender and recipient are capped at 120 characters, subject at 160, snippet at 120 and date at 40. Because those caps bound source text rather than JSON, and quote-dense content can double under escaping, the assembled result is then trimmed entry by entry until it serialises below 11,000 characters, counting what was dropped in `omitted`; the page token is bounded at 1,000. This keeps every result under the 12,000-character model projection, above which a result is replaced by a bare excerpt. The untrusted-content warning and the hint are the first fields regardless, so they survive even an excerpt. A hit whose metadata fetch fails or exceeds the turn budget keeps its identifiers and carries a `detail` note rather than failing the search. A computed `hint` asks for a narrower query above 50 estimated matches and suggests widening when nothing matched; it is never written by the model. Metadata is not a parts listing, so no attachment flag is returned; `has:attachment` remains available as a search operator. Identical searches by the same owner are served from a five-minute in-process cache.

`gmail_thread` reads one conversation oldest first, at most 12 messages, 2,500 characters per message and 6,000 characters of body text in total, reporting which messages were truncated or omitted. Every message consumes at least one character of that total, so a conversation of messages with no plain-text part is bounded by the message count rather than growing without limit. A conversation whose full form exceeds the two-megabyte response guard degrades to its message list with sender, subject and date, so the model can fall back to `gmail_read` on a specific message instead of losing the call. A message with no plain-text part is marked `bodyless`, since `gmail_read` cannot return more for it than the snippet already shown, and `truncated` means only that a plain-text body was cut. `gmail_read` still returns one message up to 16,000 characters, which can itself exceed the projection limit and be excerpted. HTML parts and attachments are never fetched or executed in any of the three. `calendar_list` reads the primary calendar with bounded time ranges. Each adapter checks the configured owner before network access. Email and event content may enter model context and is untrusted data.

> **Update, 22 November 2026 ([journal 204](journey/204-email-search-redesign.md), [email search, Phase 1](email-search.md#phase-1-tools)):** Chief failed to find monthly receipt emails that were in the mailbox, and the cause was in these tools rather than in Gmail's index: HTML-only mail (most receipts) was reduced to Gmail's snippet and marked `bodyless`, search stopped at ten hits for eleven requests, threads were cut to 2,500 characters per message and 6,000 in total, and `gmail_read` advertised 16,000 characters while the projection cut it to 8,000. Now:
>
> - **Body text.** `gmail_thread` and `gmail_read` return the plain-text part when it has content, otherwise the whole HTML part converted to reading text (`readerText`: line breaks at blocks and table rows, tabs between cells, escaped angle brackets kept, quoted and forwarded content included; the mail index keeps its own conversion and quote cut). Such a message carries `fromHtml`; `bodyless` means a message has neither part, and its snippet (at most 200 characters) stands in. HTML is converted to text only: never executed, and no link, image or attachment is fetched.
> - **Sizes.** `gmail_read` returns up to 20,000 characters of one message, with `truncated`, `nextOffset` and `totalChars` and an `offset` argument to continue. With `messageIds` (1 to 25) it reads several messages in one call, at most four requests at a time, sharing 50,000 characters fairly, with a per-message `truncated` flag and `nextOffset`, and a failed or rate-limited message reports a `detail` instead of failing the rest. A `messageId` read keeps its earlier result shape (new optional fields only); responsibility investigations still read one confirmed message per call. `gmail_thread` returns at most 50 messages, up to 20,000 characters each and 50,000 in total, shared fairly, and lists any later messages with their IDs and received times in `omittedMessages` for a `messageIds` read; the metadata fallback for a conversation past the two-megabyte guard does the same after 50. Every cut, `nextOffset` and header cap lands on a code-point boundary, and an `offset` inside a surrogate pair starts at its first half, because Postgres refuses lone surrogates in stored results.
> - **Projection.** `src/observations.ts` keeps per-operation limits: for `gmail_search`, `gmail_thread` and `gmail_read` a payload field may be 20,000 characters and the serialised result 110,000 before it is excerpted; every other tool keeps 8,000 and 12,000. The adapter shortens the longest text (then drops trailing entries) until a result serialises below 108,000, so the untrusted-content warning stays the first field; dropped search rows and thread messages are listed by ID in `omittedMessages`, and the search hint says to read them with `messageIds`.
> - **Search.** `pageSize` defaults to 20 and may be 1 to 100 (Gmail's own default page). The page's metadata comes from sequential Gmail batch requests of at most 25 parts, with rows seen in the last ten minutes served from a per-mailbox cache; rate-limited parts or batches are retried with backoff within a 15-second window per call, a part a batch did not otherwise answer is fetched once on its own, four at a time, and a row still failed or refused degrades to identifiers with a `detail` ([email search, Phase 1](email-search.md#phase-1-tools)). A maximal 100-row page serialises to about 88,000 characters, inside the projection. Each row adds `received` (Gmail's `internalDate` in Singapore time), `category` (primary, social, promotions, updates, forums) and `folder` (inbox, archived, sent, spam, trash). Calendar dates in `after:`, `before:`, `older:` and `newer:` (Gmail reads them as midnight Pacific time) are sent as epoch seconds at Singapore midnight, `older:`/`newer:` as `before:`/`after:`; relative forms, numeric values and quoted text are left alone, `query` echoes what was sent and `requestedQuery` what was asked. An empty page returns a `hint` on how to broaden; a page with a `nextPageToken` says to follow it. Gathering, mail recall's keyword searches, the daily briefing and the mail-recall eval pass `pageSize: 10`, and gathering also keeps its query text unrewritten.
> - **Rate limits.** Gmail enforces its own per-user quota. A 429, or a 403 whose error reason is a rate or quota limit (`rateLimitExceeded`, `userRateLimitExceeded`, `quotaExceeded`, or the newer ErrorInfo reason `RATE_LIMIT_EXCEEDED`), reaches the model as `RATE_LIMITED` (retryable) with "Gmail rate limited this request … Wait a few seconds and retry; the connection is fine." A `dailyLimitExceeded` refusal is `RATE_LIMITED` but not retryable, and says the daily quota is used and that Google's daily quotas reset at midnight Pacific time. Missing scopes and other 403s stay `AUTHORIZATION_REQUIRED`. Before this, both read as "reconnect if authorization expired" and mapped to `AUTHORIZATION_REQUIRED`. A rate-limited batch, batch part or batch-read message degrades only its rows with a detail saying to retry shortly, and is not fetched again at once; other 403s remain authorization failures.
> - **Request budget removed.** The per-run budget (40 requests since [journal 23](journey/23-gmail-search.md)) is gone for model tools and host callers alike, together with its error and the "turn request budget reached" rows. Journal 23 added it as the host-enforced form of its "stop after about three searches" guidance, to steer the model rather than for safety. Every run is already bounded by its tool-call, model-call and time allocations, the background callers bound their own scheduling, and Gmail's quota is enforced by Gmail and surfaces as the rate-limit message above. Its cost was real: a search cost eleven of the forty requests, so a few searches and reads exhausted a turn.
> - **Unchanged.** Gmail stays read-only, owner-only, identity-checked per mailbox with no fallback to the other one, IDs are validated before any URL, requests refuse redirects, the 2 MB and 29 MB response guards and MIME part limits stand, and the warning leads every result.

> **Update, 22 November 2026 ([journal 204](journey/204-email-search-redesign.md), [email search, Phase 2](email-search.md#phase-2-coordinator)):** the coordinator now calls these tools itself; the email agent is retired, and email text enters the coordinator's context (owner-approved). Responsibility investigations still read only a confirmed message, and `parcels` keeps its Gmail tools. Gathering drops spam and trash rows from its searches in host code, by each row's folder, and its attachment reads refuse a message labelled spam or trash (corrected the same day: an earlier version of this note said its searches never include them; Gmail honours `in:spam` in a query even inside quotes, measured, so only the host filter keeps them out; see [email search, Phase 2](email-search.md#phase-2-coordinator)). A default search already includes archived mail, and `in:anywhere` adds only spam and trash (measured; the earlier text here and in the tool description said it added archived mail). The `gmail_search` description says a row's folder, category and unread flag can be up to fifteen minutes old. `observation_read` of a stored Gmail result leads with the untrusted-content warning on every page. Gmail stays read-only, owner-only and identity-checked per mailbox.

> **Update, 22 November 2026 ([journal 204](journey/204-email-search-redesign.md), [email search, Phase 3, part 1](email-search.md#phase-3-part-1-attachments-link-targets-and-routing)):** `gmail_read` and `gmail_thread` list every attachment of each message (Gmail's part ID, name, type, size) from the payload they already fetch; a long list pages with `attachmentsOffset`. A new read-only `gmail_attachment` returns an attachment's text: a PDF's selectable text, text, CSV and calendar files as UTF-8, HTML converted to text; other types are refused, files over 20 MB are not read, and text comes in 20,000-character windows with `offset`. It reads a message in spam or trash and reports its folder; gathering's attachment reads still refuse such a message. `gmail_read` with one message takes `links: true` for the HTML part's http, https and mailto targets, each URL whole, paged with `linksOffset`, never opened. The earlier statement that no attachment operation exists no longer holds. Gmail stays read-only, owner-only and identity-checked per mailbox with no fallback, and the untrusted-content warning leads every result, the new one included.

Use `scripts/connect-gmail.mjs` and `scripts/connect-calendar.mjs` with a private desktop OAuth client JSON, output path and expected email. The loopback flows use state/PKCE, verify scopes/account identity and write private token files. Set the corresponding variables from `.env.example`; never print token files. Testing-mode OAuth grants may require reconnection.

## Sheets as viewing surfaces

Postgres is authoritative. Preparation uses Target roles / Preparation gaps / Preparation tasks. Daily use has Tasks / Notes / Schedules. Managed tabs are one-way mirrors: edits to them are overwritten on sync. The model cannot target arbitrary spreadsheets.

Use `scripts/connect-sheets.mjs` for `drive.file` plus identity authorization and `scripts/create-preparation-sheet.mjs` to provision the preparation workbook. Existing installations should reuse their configured workbook IDs. `sheet_sync` and `daily_sync` report actual results; database writes remain saved if sync fails. Cells use literal values to prevent formula execution. There is no durable Sheets synchronization outbox yet.

See [preparation setup](preparation.md), [daily assistant](daily-assistant.md) and [verification](verification.md) for limits and tested behavior. Existing grants do not permit email sending or calendar event creation.

## Connecting from the chat (22 November 2026)

> **Added 22 November 2026 ([journal 208](journey/208-google-connect-from-chat.md)).** Until now every Google connection above was made once by hand: an operator ran a `scripts/connect-*.mjs` script on a computer and put the refresh token in the server's `.env`, and a broken token could only be answered with "reconnect". Google accounts can now be connected and reconnected from the Telegram chat, the way IBKR is ([IBKR portfolio](ibkr-portfolio.md)). The `.env` tokens keep working exactly as before until the owner connects through the chat.

**The flow.** `/google` in Telegram lists the four connections (Gmail primary, Gmail second mailbox, Calendar, Sheets), each with its state (connected from the chat with its address, connected by server setup, stopped working, not connected) and a Connect or Reconnect button. "Reconnect my Gmail" in ordinary language works too: the coordinator calls `google_connect {account}` and the host sends the same button. The button is an ordinary link the host builds, so it opens Google's account picker and consent page in the phone's browser; the model never sees the link or its state. The sign-in is a standard web-client OAuth flow: `access_type=offline`, `prompt=consent select_account`, `include_granted_scopes=false`, a `login_hint` with the address configured for that connection when there is one, PKCE (S256) and a single-use state stored hashed in Postgres for ten minutes and tied to the owner (`src/google-connect.ts`, shaped like `src/ibkr/oauth.ts`). The callback at `/oauth/google/callback` claims the state before exchanging the code, checks that Google granted every scope the connection needs (extras Google reports beside them, such as `openid` or a scope the account granted this client earlier, are accepted and recorded as granted) and that the account is the expected one, seals the refresh token in `google_connections` and posts a short confirmation in the chat; the page itself only says to return to Telegram. A wrong account, a missing scope or a cancelled consent saves nothing, and the owner is told why in the chat.

| Connection           | Scopes (as its `scripts/connect-*.mjs` requests)    | Expected account                                             |
| -------------------- | --------------------------------------------------- | ------------------------------------------------------------ |
| Gmail primary        | `gmail.readonly`                                    | `GMAIL_EMAIL`                                                |
| Gmail second mailbox | `gmail.readonly`                                    | `GMAIL_SECONDARY_EMAIL`                                      |
| Calendar             | `openid`, `userinfo.email`, `calendar.events.owned` | `GMAIL_EMAIL` (as `CalendarTools` checks)                    |
| Sheets               | `openid`, `userinfo.email`, `drive.file`            | none configured: the chosen account is accepted and recorded |

**Using a connection.** Gmail, Calendar, the preparation Sheet and the daily Sheet take their refresh token from the stored connection when there is one, refreshed with the web client's ID and secret, and otherwise from the `.env` token with the existing desktop client (`googleGrant` in `src/calendar.ts`). Gmail keeps its access-token cache; each mailbox is still identity-checked against the address of its connection. The second Gmail mailbox exists when `GMAIL_SECONDARY_EMAIL` is set; with the feature on, its `.env` token may be empty and the chat connection supplies it.

**When a connection breaks.** If refreshing a stored or `.env` token fails with `invalid_grant`, the connection is marked disconnected and the owner gets one message with a reconnect button (once, until it is reconnected or the `.env` token works again). The tool error the model sees says that a reconnect button was sent. Google's rules shape this: consent must open in a real browser, not an embedded web view; a refresh token stops working when access is revoked, after six months unused, or on a password change for Gmail scopes; and an OAuth consent screen left in "Testing" status issues refresh tokens that expire after seven days.

**Storage.** Migration 037 adds `google_oauth_attempts` and `google_connections` (the brokerage tables only allow `provider='ibkr'`). Refresh tokens are sealed with `src/secret-box.ts` under a key derived (HKDF-SHA256) from the web client secret, so the feature needs no third setting; replacing that secret means reconnecting from the chat. Tokens are never logged or shown to the model. A reconnect does not revoke the earlier token, because Google's revoke ends every connection the account has with the client.

**What the owner does once in Google Cloud.** In the same Google Cloud project as the existing desktop client, create an OAuth client of type "Web application" with the authorized redirect URI `https://<public host>/oauth/google/callback`, where the public host is the one in `MINIAPP_ORIGIN` (the IBKR callback's host). Put its ID and secret in the server's `.env` as `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET`. Publish the consent screen ("In production") so refresh tokens do not expire after seven days. With either setting unset the feature is off: `/google` says Google sign-in from chat is not set up, `google_connect` is not offered, and everything else works as today. With both set, the gateway refuses to start without migration 037 or `MINIAPP_ORIGIN`.

**Rollout.** Migration, Compose and Caddy changes, so ordinary releases refuse it. After the PR merges, with `BASE` in `scripts/deploy-google-connect.py` equal to the live release, run it through the operator connection as the earlier rollouts were:

```sh
SHA=<merged main SHA>
git archive --format=tar "$SHA" -o /tmp/chief-$SHA.tar
scp /tmp/chief-$SHA.tar scripts/deploy-google-connect.py chief-prod:/tmp/
ssh chief-prod "sudo python3 /tmp/deploy-google-connect.py /tmp/chief-$SHA.tar $SHA"
```

It applies migration 037, adds the two settings to the gateway's Compose environment, starts the new gateway (feature still off, as `.env` has no web client yet), then adds the `/oauth/google/callback` route after the IBKR one in `/etc/caddy/Caddyfile`, validates and reloads Caddy and checks that the route reaches the gateway, restoring the previous Caddyfile on any failure; rerunning it after a Caddy failure installs only the route. `ops/oauth-site/Caddyfile` is the reviewed copy. Compare the uploaded script's and archive's SHA-256 with the merged ones before running it. Then the owner adds the two settings to `/opt/hermes-companion/.env`, the gateway is recreated so it reads them (`sudo docker compose --project-directory /opt/hermes-companion -p hermes-companion up -d --no-deps --no-build gateway`), and the owner sends `/google`.

> **Update, 22 November 2026 ([journal 208](journey/208-google-connect-from-chat.md#release-closure--22-november-2026)):** "feature still off, as `.env` has no web client yet" was wrong for the actual rollout. The owner created the web client and saved both settings on the server first, so the feature was on as soon as the new gateway started and no recreate was needed. Rolled out late on 22 November as `c5fa173`: migration 37 applied, the callback route answers through the public address, and the existing mailboxes still work through the `.env` tokens. No real sign-in through `/google` yet.

**Reconnecting.** Send `/google` and tap Reconnect for the connection, or ask Chief to reconnect it; when a token breaks, Chief sends the button by itself. Choose the expected account on Google's page and leave every requested permission ticked.
