# Coding model efficiency: evidence and next experiments

Research date: 9 October 2026 SGT. This is a technical research record and proposed evaluation design, not a measured benefit for Chief or a production policy change. Two independent research agents inspected primary papers, official harness documentation and first-party experiment reports. The findings below separate cheap-model evidence, stronger-model evidence and implementation examples.

## Working hypothesis

Target small, well-specified repository changes. Test whether focused tools, retained factual state, narrow handoffs and independent review let an inexpensive coder produce more accepted changes per unit of total cost. A fixed three-member squad is one candidate policy, not an established optimum. Success means independently verified scope and regression behavior; model confidence, agreement or a finished plan is insufficient.

Implementation examples are weaker evidence: [Aider edit formats](https://github.com/Aider-AI/aider/blob/main/aider/website/docs/more/edit-formats.md) show model-dependent editing representations; [repository maps](https://aider.chat/docs/repomap.html) show bounded dependency-ranked context. [OpenCode agents](https://opencode.ai/v2/docs/agents) and [Codex subagents](https://developers.openai.com/codex/subagents) already support model-specific roles. Roles, routing and cheap-model access alone do not establish a distinctive technical advantage.

## Prioritized experiments for Chief

1. **Build the disposable inference adapter and outcome accounting first.** Use the existing Python loop/OpenRouter path without publication credentials. Keep evaluator/gold material outside agent-visible workspaces, network lookup restricted and candidates graded independently. Capture complete attempts, bounded tool/model traces, actual reported usage and unknown usage separately. The offline pack currently validates fixtures/grading, not agent performance.
2. **Try atomic, guarded edits with immediate evidence.** Compare current whole-file writes with exact old-text replacement and a stale-content guard. Return a bounded applied diff or a precise mismatch/current span. Follow edits with relevant syntax/type/test diagnostics. Do not assume a particular patch format works better for Flash until measured.
3. **Narrow the implementation handoff.** Supply exact behavior, relevant files/symbols, invariants, observed reproduction and acceptance checks. Separate verified observations from hypotheses. Compare the same coder with and without this handoff before adding trained routing or more agents.
4. **Calibrate review before trusting its economics.** Use a frozen mixed pool of correct, near-correct and defective patches; reviewers see public checks and exact artifacts, never hidden outcomes. Request concrete violated requirements, code locations and reproducible consequences. Measure reviewer errors and whether rework repairs bad patches or damages good ones.
5. **Compare state-preserving context strategies.** Keep notes, receipts, task constraints and recent errors. Test selective removal of old bulky observations against current summarization, with retention probes. Measure cost and accepted outcomes together; thinking configuration may reverse the result.
6. **Recover using new causal evidence.** Distinguish stale edits, syntax/type failures and behavioral failures. Return the smallest useful expected/actual result and affected span; require a revised diagnosis before another repair. Preserve existing uncertainty/cancellation gates and allocation ceilings.

These are proposed experiments. Production retains owner-approved roles, mandatory checks/review and existing model/provider filters and shared allocations. No automatic escalation, reduced review, new dollar cap, paid trial or job resumption is authorized by this document.

## Comparison design

Freeze a complete approved task brief for all arms so implementation/review comparisons do not conflate different requirements. Measure planning separately. Keep sandbox, tools, context handling, grader and time/model/tool ceilings fixed; pin model/effort and record different actual resource usage.

| Arm | Experimental policy                                                         | Question                                  |
| --- | --------------------------------------------------------------------------- | ----------------------------------------- |
| A   | DeepSeek V4.1 Flash solo + actual checks                                    | Cheap baseline                            |
| B   | GPT-6.1 Sol high solo + same checks                                         | Stronger solo baseline                    |
| C   | Flash coder + Sol independent reviewer/rework                               | Value of strong review                    |
| D   | Flash leader orchestrates the same frozen brief, Flash coder + Sol reviewer | Incremental value of leader orchestration |

These are isolated evaluation arms, not changes to production approval or publication policy. Add cheap independent review and observed-failure escalation only after this first comparison identifies the bottleneck. Use an equal-extra-repair baseline when attributing improvements to review rather than more inference.

Start with three randomized repetitions on the six seeded Chief component fixtures as an adapter/variance pilot. The four public selections still require official environment readiness checks and separate reporting. All existing tasks are development cases with public source/grader material, not a secret holdout. Repeating ten related cases does not create thirty independent tasks. Add previously unseen multi-file requirements and freeze them before selecting a production policy.

Report acceptance/attempted with empty patches, timeouts and infrastructure failures retained; distinguish infrastructure outcomes from model failures. Total cost per accepted change is all planning/coding/review/rework/failure and sandbox/CI cost divided by accepted changes. Include unknown-accounting limits, wall-time stages/median/p90, owner intervention, incorrect approvals/all incorrect patches, incorrect rejections/all correct patches, bugs repaired and good patches broken. Track marginal benefit of additional rounds; proposed stopping thresholds need prospective tests.

## Current evidence boundary

Chief has targeted navigation, member notes/receipt retention, compaction, bounded generation recovery, repetition recovery, actual checks and exact-artifact independent review. One v2 real planning job completed; end-to-end coding/review/PR success and cost advantage remain unmeasured. The next useful result is a reproducible accepted-change comparison, not another untested abstraction or a claim that three agents necessarily outperform one.
