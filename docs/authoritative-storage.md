# Authoritative records and bounded history

Postgres remains the canonical application store. That does not imply sending the whole database to a model or keeping every trace forever. Current roles, memories, tasks, approvals, skills, schedules and canvas revisions retain their existing tables and ownership boundaries. Conversation history is historical evidence; an earlier assistant assertion cannot override a current record or establish factual correctness.

## Message storage v2

Migration 012 adds `message_contents`, `run_messages` and `conversation_messages`. A message payload is stored once per owner, identified by SHA-256 of its PostgreSQL JSONB text. Identical content can occur multiple times: ordered references preserve each occurrence. Different owners never share content identities or query results. This is payload deduplication, not semantic deduplication of statements or memories.

`runtime_runs.message_count` and `conversations.message_count` support atomic, compare-and-append writes. New run checkpoints append only the suffix since their previous successful checkpoint. A changed prefix or stale counter fails rather than overwriting saved work. The count, content and references commit in one SQL statement. Conversation completion appends the new turn only, never its earlier context. Independent runs reference repeated content rather than copying it. Canonical historical messages remain accessible even after omission from active context.

A run retains references to its initial bounded context plus messages produced during that run. The latter remain complete for investigation, including incomplete tool-call groups. References can therefore grow within a long operator-configured allocation, but old complete conversations are no longer duplicated into each run. `runtime_calls` still journals arguments, results and uncertain writes independently; observations, receipts, task checkpoints and source evidence remain intact.

The old JSON array columns remain in the schema for explicit rollback compatibility, but are empty under this runtime. New startup refuses missing migration 012 or unreconciled legacy arrays. Historical Hermes and reset archives are not migrated or erased.

## Loading and fallback reads

Foreground requests read recent conversation references. Continuations read their latest owner-scoped task run. SQL selects at most 1,000 recent references, 20 user turns and approximately 100,000 message characters before returning payloads. The context selector removes incomplete tool groups and applies the final JSON character limit. The existing smaller model-request budget is applied afterward. Full history is not loaded into the Node process on every turn.

`conversation_search(query)` uses PostgreSQL English full-text search, returning up to ten original message IDs, roles, excerpts and times. `conversation_read(id,offset)` reads one original message in 8,000-character pages. Both use authenticated identity, never a model-supplied user. Search is lexical, not semantic; it may miss paraphrases or vocabulary outside the English configuration. Background/specialist checkpoints are retained for recovery and operator inspection, not injected into the user's conversation or exposed through these conversation tools.

The model is told to retrieve omitted discussions and read current domain records rather than invent missing details. Retrieval is available, not guaranteed to be chosen correctly by every model response. Source truth remains separate from historical assistant claims. These tools are not added to specialist read allowlists.

Each conversation entry has an immutable UUID, originating run when known, and sequence position. Legacy entries use their existing conversation timestamp and no invented originating run; it is not the original per-message send time. `/reset` removes the active conversation and its references using the existing explicit reset behavior. Run references/journals remain; orphan-content cleanup is not automatic. IDs are never reused for new messages.

## Observability and retention

`history.loaded` records source kind, loaded/omitted counts and storage version without message text. Model context omissions include the earlier storage selection omissions. Existing tool execution traces record fallback reads. `scripts/storage-diagnostics.sql` returns aggregate logical payload sizes, reference counts, physical table/database sizes, detailed research-trace volume and uncertain-write count. No conversation or credential content is printed. The reviewed diagnostic handler also exposes compact storage counts and sizes through the existing production-diagnostics GitHub workflow, usable by authorized local and cloud coding tasks. Raw private message export remains separate. Logical deduplication is not a claim of equivalent physical disk savings or API cost savings. Ordinary vacuum can reuse freed space; it does not necessarily shrink database files.

No automatic retention purge is included. Detailed model-input events, source records and call results can still be large. The next retention change should first identify dependencies from active/recoverable tasks, memory provenance, evidence and saved artifacts. A candidate policy is 30 days of detailed traces with compact outcomes and explicitly retained incident/evidence records longer; this is a proposal, not an enabled timer. This milestone does not claim complete trace deduplication or raw private trace export to cloud tasks.

## Reviewed deployment and rollback

This changes both the schema and Compose migration list. Ordinary app-only releases must refuse it until an operator completes the reviewed procedure. No new infrastructure or credentials are needed.

1. Require an independent Astra review of the exact PR head, including migration and `scripts/deploy-storage.py`, and passing checks. Merge, verify the resulting main SHA and main checks. The normal release can refuse the uninstalled schema baseline; do not bypass that guard.
2. On the authorized local operations connection, upload `git archive MAIN_SHA` and the reviewed `scripts/deploy-storage.py`. The script verifies the archive's embedded SHA, takes the shared release lock and requires the documented v0.3.6 baseline `20564401c5130f79e2f90a8c802c32298c6c502e`. It refuses historical migration edits, unexpected added migrations and active work. Do not cancel a user task to deploy. The one-time script is not installed as a remote cloud capability.
3. Run `python3 SCRIPT ARCHIVE MAIN_SHA` on the existing host. It builds the candidate before downtime, stops the gateway, applies only migration 012 and starts the candidate. The migration reconstructs and compares every old array before clearing it, all in one transaction. No task, memory, role, approval or source is reset. Existing normal startup recovery may pause queued work; it never automatically resumes paused tasks.
4. On startup failure the operator script stops the candidate, rehydrates legacy arrays from normalized references, restores Compose and the prior image, then checks health. All normalized data/IDs remain. A retry reconciles legacy writes through migration 012; it verifies equality and fails on divergent histories. Manual rollback after release likewise requires stopping the gateway and running `scripts/restore-legacy-history.sql` before starting pre-v0.3.7 code. An old image alone is not a valid rollback.
5. Verify exact RELEASE, health, migration marker, aggregate storage counts and preserved domain counts. Use the production container's `HistoryStore` for a read-only bounded-history check; do not run paid model tests or forge a Telegram interaction. Run the normal GitHub release on current main afterward to verify the ordinary app pipeline with the installed baseline.
6. The operator script installs the reviewed root-owned diagnostic handler after health succeeds; the existing deploy/diagnose command permissions stay unchanged. Publish only the verified patch tag/notes. Record health separately from model/Telegram behavioral acceptance. The database migration still requires operator access; ordinary later code releases remain cloud-capable.

Rework that candidate to reference current message UUIDs or owner/run/ordinal references rather than copying entire chats, then finish revision/provenance tests and bounded memory selection.
